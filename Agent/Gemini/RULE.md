# RULE.md — Self-Storage Facility Rental and Management System

## 0. Purpose

This file defines mandatory engineering rules for the PRN222 project:

**Self-Storage Facility Rental and Management System**

All AI agents must read this file before analyzing, generating, modifying, or deleting code.

If a prompt conflicts with this file, follow this priority:

1. The user's newest explicit instruction.
2. The real SQL Server database schema.
3. This RULE.md.
4. Existing project conventions.
5. Agent assumptions.

Never silently override the database schema.

## 2. Architecture

The project MUST use exactly three application layers:

```text
Presentation
    ↓
BusinessLogic
    ↓
DataAccess
    ↓
SQL Server
```

Recommended solution structure:

```text
SelfStorageManagementSystem.sln

src/
├── SelfStorageManagementSystem.Presentation/
├── SelfStorageManagementSystem.BusinessLogic/
└── SelfStorageManagementSystem.DataAccess/
```

Allowed project references:

```text
Presentation -> BusinessLogic
BusinessLogic -> DataAccess
DataAccess -> no application-layer project
```

Forbidden references:

```text
DataAccess -> BusinessLogic
DataAccess -> Presentation
BusinessLogic -> Presentation
```

Avoid circular dependencies.

Presentation MUST NOT directly access DbContext.

Presentation MUST NOT directly access repositories.

BusinessLogic MUST NOT contain raw SQL/database infrastructure code.

DataAccess MUST NOT contain HTTP/controller logic.

---

## 3. Database Is the Source of Truth

This is a DATABASE-FIRST project.

The existing SQL Server database is the authoritative source for:

- tables
- columns
- primary keys
- foreign keys
- nullability
- indexes
- unique constraints
- relationships
- data types
- default constraints
- naming

Never invent a table, column, key, or relationship that is not present in the supplied database/schema unless the user explicitly requests a database change.

Never rename database-generated Entity properties just for style without approval.

Never convert the project to Code First.

Never create an initial migration representing the existing database.

Do NOT use `EnsureCreated()`.

Do NOT call `Database.Migrate()` for the existing DB-first schema unless the project is deliberately migrated to a migration-based workflow later.

---

## 4. EF Core Database-First Rules

Entity classes and DbContext MUST be generated from the SQL Server database using EF Core reverse engineering.

Preferred command pattern:

```bash
dotnet ef dbcontext scaffold "<CONNECTION_STRING>" \
  Microsoft.EntityFrameworkCore.SqlServer \
  --project src/SelfStorageManagementSystem.DataAccess \
  --startup-project src/SelfStorageManagementSystem.Presentation \
  --context SelfStorageDbContext \
  --context-dir Context \
  --output-dir Entities \
  --no-onconfiguring \
  --use-database-names \
  --force
```

Adjust only when technically necessary.

`--no-onconfiguring` is mandatory unless there is a concrete reason not to use it.

The connection string MUST NOT be embedded in generated DbContext code.

The connection string MUST NOT be committed with production credentials.

Generated database code belongs in:

```text
DataAccess/
├── Context/
│   └── SelfStorageDbContext.cs
└── Entities/
    └── *.cs
```

## 5. Generated-Code Protection

Treat files generated by `dotnet ef dbcontext scaffold` as generated code.

Do NOT manually add business logic to:

```text
DataAccess/Entities/*.cs
DataAccess/Context/SelfStorageDbContext.cs
```

Do NOT manually add validation, DTO logic, service logic, API logic, authorization logic, or helper methods into scaffolded entity files.

Reason: re-scaffolding with `--force` may overwrite them.

If generated entities require custom behavior, use separate files/classes where possible, such as:

```text
Entities/Extensions/
Partials/
```

Only use partial classes if scaffolded entities are declared `partial`.

Never rely on manual changes inside a file that will be overwritten by re-scaffolding.

## 6. Database Inspection Before Coding

Before generating feature code, inspect the actual database/schema.

The agent MUST identify:

- all tables
- primary keys
- foreign keys
- navigation relationships
- nullable columns
- enum/status-like columns
- monetary columns
- date/time columns
- soft-delete columns if any
- audit fields if any
- unique constraints
- indexes relevant to lookup/reservation/payment flows

Do not infer a business rule merely from a column name when the database does not prove it.

If a database name is ambiguous, report the ambiguity instead of inventing a meaning.

## 7. DataAccess Responsibilities

DataAccess is responsible for persistence.

Recommended structure:

```text
SelfStorageManagementSystem.DataAccess/
├── Context/
├── Entities/
├── Repositories/
│   ├── Interfaces/
│   └── Implementations/
└── DependencyInjection/
```

Repository responsibilities:

- query EF Core
- add/update/delete tracked entities
- persistence-related filters
- Include/ThenInclude when required
- async DB operations

Repository MUST NOT implement business rules such as:

- whether a customer may reserve a unit
- whether a reservation may be cancelled
- deposit policy
- overdue policy
- role-based business decisions
- pricing policy
- refund eligibility

Those belong in BusinessLogic.

## 8. Repository Rules

Use repositories only when they provide value.

A simple generic repository is acceptable for common CRUD:

```csharp
IRepository<T>
Repository<T>
```

Useful operations may include:

```csharp
Task<List<T>> GetAllAsync(CancellationToken cancellationToken = default);
Task<T?> GetByIdAsync(object id, CancellationToken cancellationToken = default);
Task AddAsync(T entity, CancellationToken cancellationToken = default);
void Update(T entity);
void Delete(T entity);
Task<bool> AnyAsync(Expression<Func<T, bool>> predicate, CancellationToken cancellationToken = default);
Task<T?> FirstOrDefaultAsync(Expression<Func<T, bool>> predicate, CancellationToken cancellationToken = default);
Task<List<T>> FindAsync(Expression<Func<T, bool>> predicate, CancellationToken cancellationToken = default);
Task<int> SaveChangesAsync(CancellationToken cancellationToken = default);
```

Do NOT force all complex queries into a generic repository.

Create domain-specific repositories when a query genuinely needs:

- multiple joins/includes
- aggregate queries
- reservation availability queries
- report queries
- complex filtering
- transaction-specific persistence logic

Do not create empty repository interfaces for every entity automatically unless they have domain-specific behavior.

## 9. BusinessLogic Responsibilities

BusinessLogic contains use cases and business rules.

Recommended structure:

```text
SelfStorageManagementSystem.BusinessLogic/
├── DTOs/
│   ├── Requests/
│   └── Responses/
├── Services/
│   ├── Interfaces/
│   └── Implementations/
├── Common/
├── Exceptions/
├── Mappings/
└── DependencyInjection/
```

Service responsibilities:

- validate business conditions
- coordinate repositories
- calculate values
- enforce workflows/status transitions
- map Entity <-> DTO
- throw meaningful application exceptions
- return DTOs, not EF entities

Do NOT expose EF Core entities directly from Controllers.

Do NOT make Controllers perform entity-to-DTO mapping unless trivial and explicitly justified.

Initially prefer explicit/manual mapping so the flow is visible for PRN222.

Do not add AutoMapper unless explicitly requested.

## 11. DTO Rules

API contracts MUST use DTOs.

Naming examples:

```text
CreateReservationRequest
UpdateReservationRequest
ReservationResponse
ReservationDetailResponse
FacilityListItemResponse
```

Do not reuse one DTO for unrelated create/update/detail/list operations merely to reduce file count.

Request DTOs should contain only fields clients are allowed to send.

Response DTOs should contain only fields clients should receive.

Never trust client-provided values for server-controlled fields such as:

- database IDs generated by DB
- created timestamps
- created-by values
- final calculated amounts
- authorization roles
- status transitions controlled by business rules

---

## 12. API Response Rules

Use a simple shared response wrapper where useful:

```csharp
public class ApiResponse<T>
{
    public bool Success { get; set; }
    public string Message { get; set; } = string.Empty;
    public T? Data { get; set; }
    public object? Errors { get; set; }
}
```

Do not nest response wrappers.

Do not return HTTP 200 for every failure.

Use correct HTTP status codes.

Typical mapping:

```text
200 OK              successful read/update
201 Created         successful create
204 No Content      successful delete with no response body, if chosen
400 Bad Request     invalid request/business input
401 Unauthorized    unauthenticated
403 Forbidden       authenticated but not allowed
404 Not Found       resource not found
409 Conflict        state/uniqueness/concurrency conflict
500 Internal Error  unexpected server failure
```

---

## 13. Exception Handling

Use centralized exception handling.

Preferred approach for .NET 8:

```text
IExceptionHandler
```

or a single global middleware when justified.

Do not duplicate try/catch in every controller.

Recommended custom exceptions:

```text
BadRequestException
NotFoundException
ConflictException
ForbiddenException
UnauthorizedException
```

Do not return stack traces in Production.

Unexpected exceptions MUST be logged with `ILogger<T>`.

---

## 14. Pagination

Use pagination for endpoints that may return large lists.

Recommended models:

```text
PagedRequest
PagedResult<T>
```

Defaults:

```text
PageNumber = 1
PageSize = 10
MaxPageSize = 100
```

Pagination must be executed at database/query level before materializing the full dataset whenever possible.

Avoid:

```csharp
var all = await query.ToListAsync();
var page = all.Skip(...).Take(...);
```

Prefer SQL-translated pagination:

```csharp
await query
    .Skip(...)
    .Take(...)
    .ToListAsync();
```

---

## 15. Async and Cancellation

Use async EF Core APIs for I/O:

```text
ToListAsync
SingleOrDefaultAsync
FirstOrDefaultAsync
AnyAsync
CountAsync
SaveChangesAsync
```

Do not use:

```text
.Result
.Wait()
```

Public service/repository async methods should support `CancellationToken` where practical.

## 16. Dependency Injection

Each layer registers its own dependencies.

DataAccess:

```csharp
services.AddDataAccess(configuration);
```

BusinessLogic:

```csharp
services.AddBusinessLogic();
```

Presentation `Program.cs` should remain concise.

DbContext registration belongs to DataAccess dependency injection.

Example:

```csharp
services.AddDbContext<SelfStorageDbContext>(options =>
    options.UseSqlServer(
        configuration.GetConnectionString("DefaultConnection")));
```

Do not instantiate DbContext manually with `new`.

{
  "ConnectionStrings": {
    "DefaultConnection": ""
  }
}

Development credentials may be stored in:

- User Secrets
- environment variables
- local ignored development configuration

Never print full connection strings containing secrets into logs.

## 18. SQL Server Conventions

The real DB type definitions win over C# assumptions.

Pay attention to:

- `decimal(p,s)` for money/fees
- `datetime2` where present
- Unicode `nvarchar`
- nullable vs non-nullable columns
- identity/generated columns
- computed/default columns
- unique indexes
- FK delete behaviors

Never use `double` or `float` for money when DB uses decimal/numeric.

Do not silently change SQL types.

---

## 19. Transactions and Concurrency

Do not add explicit transactions to every operation.

Use explicit transactions only when one business operation requires multiple writes that must succeed/fail together.

For reservation/unit allocation/payment-sensitive flows, inspect the real DB first and then decide transaction/concurrency strategy.

Do not invent concurrency tokens.

If the DB contains `rowversion`/timestamp concurrency columns, preserve and use them correctly.

---

## 20. Authentication and Authorization

Do NOT implement authentication/authorization until requested.

When implemented later:

- authentication belongs in Presentation/BusinessLogic boundaries as appropriate
- authorization must respect role and facility scope
- never trust role/facility IDs sent by the client without server-side verification
- System Administrator, Business Operations Manager, Facility Manager, Facility Staff, and Storage Customer have distinct access scopes

Do not implement JWT placeholders that create fake security.

Known roles:

1. Storage Customer
2. Facility Staff
3. Facility Manager
4. Business Operations Manager
5. System Administrator

Do not rename these roles or change their semantics without explicit instruction.

Facility-scoped roles must not automatically access data from all facilities.

Actual role storage/schema must come from the database.

## 22. Core Business Scope

Known system scope includes:

### Storage Customer

- browse facilities
- browse unit types/sizes/prices/availability
- reserve storage
- pay deposit/rent/renewal/extra charges
- scheduled check-in
- manage rented units
- submit support requests

### Facility Staff

- verify reservation on arrival
- support check-in/handover
- update unit status
- inspect unit return
- handle on-site support
- track daily operational tasks

### Facility Manager

- manage units within assigned facility
- assign units
- monitor customers/contracts/payment status
- manage handover/return/renewal/overdue process
- assign staff
- view facility reports

### Business Operations Manager

- manage all facilities
- manage global rental policies
- manage price ranges/fees/discount policies
- monitor revenue/usage/performance
- system-wide reporting

### System Administrator

- manage accounts
- manage roles
- manage data-access permissions
- track login/activity logs

These are product requirements, not permission to invent missing DB tables.

If the current DB does not support one of these requirements, report the gap.

## 23. Status and Enum-Like Fields

Do NOT create C# enums merely because a DB column appears to contain status text/int values.

First inspect:

- CHECK constraints
- lookup tables
- seeded values
- documentation
- existing code

Only create an enum when its allowed values are proven and stable.

If status values are not fully known, preserve the generated type and report the uncertainty.

---

## 24. Delete Behavior

Do not assume hard delete.

Before implementing delete:

- inspect FK constraints
- inspect `IsDeleted`/`DeletedAt` or equivalent
- inspect business requirements
- inspect audit requirements

If soft-delete exists, use it consistently.

If no delete strategy is proven, do not invent one.

## 25. Naming

C# conventions:

```text
PascalCase  -> classes, interfaces, methods, public properties
camelCase   -> local variables, parameters, private fields
IName       -> interfaces
Async       -> asynchronous method suffix
```

Database-generated names may follow database naming when scaffolded with `--use-database-names`.

Do not casually rename scaffolded models.

DTO/service/API naming should use clean C# conventions.

## 30. Build Discipline

After each implementation step, run:

```bash
dotnet restore
dotnet build
```

The agent must fix compile errors introduced by its own changes before ending the task.

Do not leave obvious:

- compilation errors
- missing project references
- broken namespaces
- duplicate DI registrations
- missing packages
- invalid nullable usage

If a failure depends on missing DB credentials or unavailable infrastructure, state exactly what could not be verified.

## 31. Change Discipline

Before editing:

1. inspect existing code
2. inspect project references
3. inspect database-generated code when relevant
4. identify files that will change

During editing:

- make the smallest coherent change
- preserve existing working behavior
- do not rewrite unrelated files
- do not mass-format the repository without permission

After editing:

1. run build
2. review diff
3. verify architecture rules
4. summarize changed files
